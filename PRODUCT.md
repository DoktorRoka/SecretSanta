# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Преподаватели и студенты одной университетской кафедры (профиль — информатика),
обменивающиеся подарками вживую, на реальном праздничном мероприятии.

- **Организатор** — один из участников (преподаватель или студент). Создаёт
  комнату, получает код, рассылает его по своим каналам, следит за списком и
  запускает жеребьёвку. Часто это тот же человек, что и самый занятой
  участник, поэтому путь организатора должен быть коротким и однозначным.
- **Участник** — заполняет короткую анкету (имя, группа/должность, контакт,
  пожелания) и позже заходит за своим получателем. Заходят в основном с
  телефона, одна ссылка на всех, часто из мессенджера; часть — с ПК.

## Product Purpose

Заменить бумажную жеребьёвку в шапке на честный цифровой обмен подарками
внутри одной группы. Продукт избавляет от самоподарков и путаницы, оставляет
анкеты в одном месте и открывает каждому ровно одного получателя. Успех —
мероприятие проходит без споров и без утечки «кто кому дарит».

## Positioning

Жеребьёвка честная и слепая: ни участник, ни организатор, ни суперадминистратор
не видят пары «кто кому дарит» — каждый видит только своего получателя. Комнаты
изолированы друг от друга коротким кодом. Всё живёт на одном дешёвом PHP-хостинге
(SQLite), без фреймворков, Composer, npm-сборки и CDN: одна ссылка, телефон и ПК.

## Operating Context

- Публикация на виртуальном PHP-хостинге (Reg.ru), корень сайта — `public_html/`.
- Один `index.html`, hash-роутинг, свой CSS и vanilla JS на ES-модулях; строгая
  CSP (`script-src 'self'`, без inline-скриптов и стилей).
- Распространение — по ссылке из мессенджера; код комнаты присылает организатор.
- Язык интерфейса — русский; данные персональные (ФЗ-152, есть чекбокс согласия).
- Мероприятие ограничено во времени: данные собираются на время события и
  удаляются после него.

## Capabilities and Constraints

- Раздельные действия «создать комнату» и «присоединиться по коду»; типы комнат
  `student` / `teacher`, роль должна совпадать с типом.
- Один замкнутый цикл жеребьёвки (никто не дарит себе, при 3+ участниках нет
  взаимных пар), минимум 3 участника; после жеребьёвки правки и удаление закрыты,
  сброс жеребьёвки — только суперадминистратор.
- Восстановление доступа: организатор сбрасывает участнику временный ПИН; пароль
  организатора сбрасывает суперадмин.
- Технически: без фреймворков, без сборки, без внешних запросов; иконки — inline
  SVG, декор — CSS и `data:`-изображения.
- Вне рамок: любые изменения логики, API, текстов и структуры экранов — этот
  редизайн визуальный.

## Brand Commitments

- Название продукта — «Тайный Санта».
- **Тёмная тема и новогодняя палитра из ТЗ сохраняются** (выбор пользователя):
  фон `#0E1A2B`, поверхности `#16263D`, текст `#F4F7FB`, акцент `#E5384F`,
  вторичный `#2FA37A`, золото `#F2C14E`. Тёмный фон и праздничные акценты —
  обязательная часть облика.
- Жёсткие запреты из `STYLE.md` (обязательны):
  - никаких 3D-блобов;
  - никаких эмодзи;
  - никаких иконок ракет и искр.
- Никаких внешних ресурсов: без CDN, внешних шрифтов и картинок.
- В git — conventional commits.

## Evidence on Hand

- Реального контента, отзывов, логотипов и фотографий нет; всё, что нужно
  интерфейсу, авторизуется на месте и не выдаётся за настоящие данные.
- Есть скелет-приложение (PHP API + SPA), ТЗ `TASK/TASK.md` и аудит `audits/`.

## Product Principles

1. Честность важнее эффекта: интерфейс нигде не должен намекать, что кто-то
   может подглядеть пары.
2. Одна ссылка, телефон в руке: короткий путь от входа до действия.
3. Праздник без детскости: тёплый новогодний характер, но сайт реального
   мероприятия, а не открытка.
4. Ничего лишнего на низком хостинге: только свой CSS и inline SVG.
5. Видимый порядок: пользователь всегда понимает, в какой комнате он находится
   и на каком шаге.

## Accessibility & Inclusion

- Mobile-first, зоны нажатия ≥ 44 px, поля ≥ 16 px (iOS без авто-зума),
  `env(safe-area-inset-*)`.
- Контраст AA, видимый фокус, учёт `prefers-reduced-motion`, `<noscript>`.
- Lighthouse mobile: Accessibility и Best Practices не ниже 90.
